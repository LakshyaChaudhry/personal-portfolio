I spent the summer in San Jose on Cisco's AI Defense team, working on agentic AI security.

That sentence is the resume version. The actual problem, at a level I can talk about, is simpler: an agent can look fine at the last token and still have gone off the rails three tool calls ago. If you only score the final answer, you miss it.

This is the public version. No internal systems, no product names, no architecture. The useful part is the industry-standard stuff: how you think about bad agent behavior when the failure is a sequence, not a single string.

## Agents fail over time

Most public LLM security still looks like output scanning. The model says something. You classify the something. If it is bad, you block it.

Agents break that. They call tools, write memory, talk to other agents, and only later produce a user-visible answer. A compromise can live in the trace. The final message can still read like a helpful assistant.

So the question is not only "is this sentence unsafe?" It is "does this trajectory violate something we actually care about?"

That is a different object. You need labels on traces, not just on completions. You need a way to talk about order. And you need a detector that is allowed to be wrong in a way you can explain, because nobody ships a black-box blocker into an enterprise product and hopes.

I am not going to describe how we built that. The public takeaway is the unit of analysis: for agents, the trace is the thing you evaluate.

## Evaluation is the whole job

I got pretty obsessive about the evaluation loop: labeled examples, a detector, metrics, then the unfun part where you pick a threshold and watch precision fall off a cliff.

Things that sound basic and were not:

- Reproducing a published benchmark number *before* you trust your own setup. If you cannot hit the paper's number on their data, your pipeline is lying to you. I have been burned by this in research already (artifact scores that look perfect until you fix the prompt formatting). Same lesson, different building.
- Calibration. The labels have to match how the detector is actually used. A corpus of obviously-malicious traces trains a detector that is bored by real traffic.
- The operating point. A high-AUC model can still be useless at the threshold you ship. Security teams live there, not on the ROC curve.

The useful intern skill was turning a fuzzy requirement ("the agent should not do this kind of thing") into something a machine can fail, then measuring whether it actually does.

## What I am taking with me

A few things survived contact with a real team:

- Trace-level monitoring is the right unit for agents. Output-only scanners are a floor, not a ceiling.
- AUC is a research metric. The threshold is a product decision.
- Reproducing someone else's number is how you debug your own pipeline.
- The work is not done until someone else can run it. Feature branches, stacked PRs, code review, a handoff doc. Unsexy. Required.

The through-line with the ICML papers is not a coincidence. Those papers argue that you cannot detect alignment faking by looking at the final answer, because the final answer is often correct. The internship was the enterprise version of the same instinct: the failure is in the sequence, not the last string the user sees.

I cannot say much more than that, which is the point. If you want methods, wait for whatever the team publishes. If you want the shape of the problem, it is this: agents fail over time, and detectors that cannot see time are going to miss them.
